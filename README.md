# exchange_rate

## Запуск проекта

Перейти в папку проекта:

```bash
cd ~/exchange_rate
```

Собрать Docker-контейнеры:

```bash
docker compose build --no-cache
```

Запустить контейнеры:

```bash
docker compose up -d
```

## Сбор курсов

Запустить постановку очереди для будущего сбора данных за указанное количество дней:

```bash
docker compose exec php php bin/console rate:collect n
```

Например, за 10 дней:

```bash
docker compose exec php php bin/console rate:collect 10
```

## Получение курса

Получить курс валюты за указанную дату:

```bash
docker compose exec php php bin/console rate:get YYYY-MM-DD CURRENCY
```

Например:

```bash
docker compose exec php php bin/console rate:get 2026-09-29 USD
```

По умолчанию используется:

* базовая валюта — `RUB`;
* источник — `cbr`.

Можно указать базовую валюту:

```bash
docker compose exec php php bin/console rate:get 2026-09-29 USD EUR
```

Можно указать источник:

```bash
docker compose exec php php bin/console rate:get 2026-09-29 USD RUB --source=cbr
```

Команда возвращает курс за указанную дату, разницу с предыдущим торговым днём и статус получения данных.


## Запуск worker-а (вручную; worker запускается автоматически с контейнером)

```bash
docker compose exec php php bin/console rate:worker
```


## Архитектурные решения и направления дальнейшего развития

### ExchangeRateDay и управление процессом сбора

Таблица `ExchangeRateDay` в текущей реализации выполняет преимущественно информационную и статусную функцию: она фиксирует необходимость получения данных за конкретную дату и текущий статус обработки. На данном этапе она не является полноценным механизмом координации потоков между MySQL и RabbitMQ.

В дальнейшем этот слой может быть расширен до полноценного механизма управления состоянием задач. Это позволит более строго контролировать жизненный цикл задания, количество попыток обработки, повторную постановку задач в очередь и избежать потенциальных конфликтов при увеличении количества worker'ов, заданного через `WORKER_COUNT`.

### Получение отсутствующих данных

При выполнении команды `rate:get` сначала выполняется поиск данных в Redis-кэше, после чего выполняется проверка основной базы данных. Если необходимые данные отсутствуют и в кэше, и в MySQL, соответствующая дата фиксируется в `ExchangeRateDay`, а задача передаётся в RabbitMQ для последующего сбора данных worker'ом.

В текущей реализации пользователь может повторно выполнить команду после завершения фоновой обработки. В качестве следующего шага развития можно добавить автоматический механизм ожидания и повторной проверки состояния задачи. В таком случае пользователю достаточно будет один раз запросить курс: приложение поставит задачу в очередь, дождётся её обработки и автоматически вернёт полученные данные без необходимости повторного запуска команды.

### Определение предыдущего торгового дня

При выполнении `rate:get` необходимо получить не только курс за запрошенную дату, но и значение за предыдущий торговый день.

В текущей реализации под предыдущим торговым днём понимается предыдущий будний день — с понедельника по пятницу, без учёта субботы и воскресенья.

При этом логика определения даты изолирована и может быть расширена в дальнейшем. Например, можно добавить различные стратегии расчёта предыдущей даты и возможность выбора соответствующего поведения через параметры консольной команды.

Это позволит учитывать более сложные бизнес-правила, например сценарий, при котором для понедельника предыдущей датой считается воскресенье, либо учитывать официальные праздничные дни и календарь конкретного рынка.

### Ограничение нагрузки на CBR

При работе worker'ов добавлены задержки между операциями, чтобы ограничить интенсивность запросов к CBR и не создавать избыточную нагрузку на внешний сервис.

Текущий механизм является сознательно простым и достаточным для поставленного технического задания. При дальнейшем развитии проекта его можно заменить на более полноценный механизм управления запросами: централизованный rate limiting, backoff/retry policies или отдельный HTTP-клиент с настройкой таймаутов, повторных запросов и сетевых параметров.

Использование прокси и других механизмов распределения сетевой нагрузки также возможно, однако для текущего объёма задачи такая инфраструктура была бы избыточной.

### Поддержка нескольких источников курсов

Модель данных изначально предусматривает возможность получения курсов не только из CBR.

В обеих основных таблицах источник данных является отдельным атрибутом, поэтому в дальнейшем можно добавить другие источники курсов без необходимости менять основную модель хранения данных. Это позволяет расширять систему, например, дополнительными поставщиками финансовых данных, сохраняя единый механизм обработки, кэширования и получения курсов.

### Запуск приложения

Проект спроектирован как самодостаточное backend-приложение и запускается из коробки согласно инструкции в `README.md`.

Docker Compose поднимает необходимые инфраструктурные компоненты приложения:

* PHP-контейнер
* MySQL
* Redis
* RabbitMQ
* необходимое количество worker-контейнеров

При запуске устанавливаются PHP-зависимости через Composer и выполняются необходимые Doctrine migrations. Таким образом, для первоначального запуска не требуется вручную устанавливать зависимости или выполнять миграции внутри контейнеров.

Количество worker'ов может быть изменено через переменную окружения `WORKER_COUNT`, что позволяет масштабировать обработку фоновых задач без изменения кода приложения.

Такой подход позволяет получить воспроизводимое окружение разработки и демонстрации: после сборки и запуска Docker Compose приложение самостоятельно подготавливает необходимые зависимости, базу данных и инфраструктуру очередей и кэширования.
